# V76 discovery-clean active-sensing source census plan

## Purpose

The next missing evidence is discovery-clean confirmation of the V74–V75
mechanism. V75 cannot fill that role because a paint-family implementation was
structurally exposed in V68. V76 therefore freezes how new sources will be
found, excluded, and assigned to scientific roles before any new candidate
implementation or policy outcome is inspected.

This stage produces only a metadata inventory and a deterministic role
partition. It does not select a favorable policy, validate source arrays,
construct an adapter, or compute value, regret, EIG, mutual information, or an
optimal action.

## Metadata firewall

The census may search scholarly indexes, package indexes, benchmark catalogs,
and public repository landing pages. It may record canonical URLs, licenses,
papers, releases, remote commit identifiers, top-level descriptions, and
high-level task features stated in abstracts, package metadata, or top-level
README text.

Before the inventory is locked, it may not clone or download a candidate,
open implementation/model/configuration/test/notebook/data files, run a
simulator or parser, inspect probability or reward arrays, or calculate any
decision statistic. Search results cannot be filtered using an implementation
diagnostic or a favorable outcome.

## Discovery-clean exclusion rule

The exclusion unit is deliberately broad. A repository, benchmark lineage, or
domain family is exposed if this project has ever previewed, structurally
inspected, parsed, executed, partitioned, or scored it. Exposure does not
require a prior policy value. Consequently the complete POBAX and Cassandra
classic-POMDP sources, every repository inspected in the V72 census, the IMPRL
repositories, pomdp-py, NOVA, and the Tiger, RockSample, paint, maintenance,
and engineered-oracle families are ineligible.

This rule is stricter than outcome untouchedness. It is what makes a future
confirmation legitimately discovery clean.

## Provisional metadata gates

A candidate family remains provisionally eligible only if public metadata
supports all of the following:

- identifiable license or reuse terms;
- no repository or domain-family overlap with the exposure registry;
- an explicit partially observed or latent physical condition;
- a state-informative sensing or inspection action;
- delayed state-dependent consequences of a later control;
- a source-described reference, calibration, or cross-sensor comparison
  pathway; and
- apparent finite exact tractability within the frozen envelope.

These are only metadata gates. Structural and economic eligibility remain
unknown until later, separately locked stages.

## Deterministic role assignment

The metadata census must find at least two repository-distinct eligible domain
families. Each identity is the canonical repository URL, pinned remote commit,
and canonical domain-family name. Candidates are ordered by the SHA-256 digest
of that identity. The first becomes development; the second and later become
protected confirmation candidates. Manual swapping is forbidden.

If fewer than two families qualify, V76 freezes a source-feasibility deferral.
It must not broaden the exposure rule, weaken a gate, return to a prior source,
or open implementation files to look for a more favorable candidate.

## Already-registered later gates

After the metadata inventory and roles are locked, only the development source
may be opened. A structural audit must show source-native actions, dynamics,
rewards, observation likelihoods, and a source-native reference pathway. The
only allowed project layer is a persistent uniform-prior permutation over
source-native observation labels; no action, beacon, reward, transition, or
observation noise may be added. Every reachable point-model observation branch
must have common positive support, and no known-reward route may bypass
sensing.

The source must fit the registered exact envelope: at most 64 physical states,
10 actions, 8 observations, six actions of horizon, two million Bellman nodes,
and 64 MiB of dense kernels. The horizon is the shortest source-valid sequence
that contains reference sensing, target sensing, and delayed state-dependent
control.

Before any optimal planner is run, a fixed source-native
reference-sense/target-sense/contingent-control policy must beat exhaustive
open loop by at least `0.015` of the finite-horizon source reward span, with at
least `0.005` additional normalized margin. Failure freezes a negative
feasibility result; it does not authorize tuning or replacement.

Only a one-shot development pass can authorize a separate protected
confirmation design lock. Until then, confirmation implementations and all
confirmation outcomes remain unopened.
