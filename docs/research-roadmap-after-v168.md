# Research roadmap after V168

## Current evidence

The program now has three cleanly separated results:

1. **Track A — external open-set language:** the V164 local residual protocol is negative and closed. Response
   formatting improved, but novelty recall remained zero and regret worsened; protected MASSIVE transfer is sealed.
2. **Track C — factored ontology uncertainty:** V165–V166 show exact model-free version-space construction, and
   corrected V167 shows positive value from class-balanced, cost-sensitive adaptive interventions. These are
   project-authored finite-DSL development results; V167's costs and losses were development-informed.
3. **Track B — reversible fixed-ontology control:** V168 shows exact preview, commit, verification, fault detection,
   provenance, and rollback on 132 project-authored simulated development fixtures. It is not deployment evidence.

## Next sequence

### 1. Fresh planner confirmation

Construct a new finite-DSL constraint-state population that excludes every V165 ambiguous evidence pattern. Freeze
its generator, membership, and identities before scoring. Reuse V167's class-balanced prior, loss matrix, 0.1 query
cost, two-query horizon, policies, and tie-breaks unchanged. Do not inspect policy scores while selecting cases.

The confirmation must report opportunity as well as performance: class coverage, query variability, positive
value-of-information prevalence, history-dependent action prevalence, exact-Bayes regret against greedy and
open-loop controls, and any structural state where querying has no value. A negative or mixed result is retained;
no tuning on the fresh population is allowed.

### 2. Stateful sandbox confirmation

Keep V168's ontology and engine contract fixed. Generate fresh multi-transaction sequences with revision races,
replay, crash points, partial-write injection, repeated rollback, provenance restart verification, and atomic
multi-entity updates. Use a separately frozen seed or exhaustive bounded enumeration, not hand-selected examples.
The engine must preserve serializable final state, invariant safety, idempotent rejection, recovery, and log-chain
integrity. Real services and tools remain absent.

### 3. Controlled integration only after both confirmations

If the two isolated confirmations pass, connect only trusted fixed-ontology decisions to the reversible sandbox in
a new shadow integration study. Provisional candidates stay outside. The planner may choose simulated inspection
or deferral; it may not authorize a commit. Deterministic validation and the independent verifier retain final
commit authority.

### 4. Model policy

No LLM is justified on V166's empty residual or in V168's typed transaction engine. A local model becomes eligible
only if a separately locked fresh language interface leaves a nonempty, truth-free semantic residual. It remains a
candidate-set proposer behind exact validation. An API model may be an optional capacity comparator, never a
runtime dependency or authority source.

## Standing boundaries

- Project-authored, procedurally generated, or model-generated records are never described as human-authored.
- Development-informed results are not promoted to fresh confirmation.
- Permanent ontology registration, provisional-to-trusted promotion, real service calls, and real execution remain
  outside the current program.
- Every new population, policy, integration, or access escalation requires its own prospective lock.
