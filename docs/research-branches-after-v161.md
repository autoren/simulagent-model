## Program objective

Advance the project through three scientifically and operationally isolated tracks:

1. controlled external open-set language transfer;
2. fixed-ontology reversible sandbox execution; and
3. shadow-only definition-conditioned ontology acquisition.

The tracks may share frozen infrastructure, but an outcome in one track cannot authorize data access,
model use, ontology promotion, action, or execution in another. They may be integrated only after each has
passed a separately preregistered fresh evaluation.

Across all tracks, authoritative state remains deterministic and immutable except through a validated
typed transition. Every local or API language model is permanently non-authoritative. The complete safe
hypothesis set must be retained, abstention must remain operational, and no real service call or external
side effect is authorized.

## Track A: controlled external open-set language transfer

### Question

Can independently authored language be separated into declared known intents, unfamiliar surfaces of
declared intents, valid but undeclared intents, and unsupported requests without unsafe false-known
acceptance?

### Current evidence

V161 froze 384 unused MASSIVE identifiers, balanced across four structural classes and two disjoint roles.
It is a population-feasibility result only. It contains no extracted language and evaluates no interface,
policy, or model.

V161 is not a direct transfer confirmation of V160. V160 tested a finite relation-alias grammar; V161 tests
open-set capability recognition over source intent and scenario structure. MASSIVE evidence must therefore
be reported as controlled record-disjoint open-set transfer, not relational-codebook transfer or
unrestricted open-world understanding.

### Immediate sequence

1. Prospectively lock exact automatic extraction of only the V161-selected records.
2. Emit immutable development and protected artifacts; keep protected language unread during development.
3. Freeze extraction identities, payload hashes, structural reconstruction, and access counters.
4. Separately preregister deterministic development controls before scoring an interface.
5. Compare complete-catalog retrieval, conservative novelty/status rules, always-ask or abstain, and oracle
   controls.
6. Define any residual model-eligible subset prospectively. A local LLM may be tested only on that residual
   as a bounded candidate proposer; truncation or malformed output is abstention.
7. Open the protected role only after all development gates and the exact protected evaluator are frozen.

An API, ensemble, adapter, or trained likelihood is not required or currently authorized. A future API
condition may be an optional capacity control, never a system dependency.

### Separate relational-language confirmation

V160's actual transfer question remains open: can independently authored relational language be translated
into its finite relation codebook while unknown aliases and cross-query relations fall back safely? That
requires a separate externally grounded or independently authored population with relation-level truth.
MASSIVE intent labels cannot answer this question by themselves.

## Track B: fixed-ontology reversible sandbox execution

### Question

Can the existing framework safely control trusted state when the ontology and supported input interface are
fixed?

### Required pipeline

```text
supported request
    -> clarification or inspection
    -> typed proposed patch
    -> reversible preview
    -> deterministic invariant checks
    -> sandbox commit
    -> independent state verification
    -> rollback or retained simulated state
```

This track must use a simulated state store, reversible transactions, an immutable provenance log, and a
verifier independent of the proposing component. It tests end-to-end control plumbing, not open-language
understanding or ontology learning.

### Gates

- exact target-state agreement;
- zero unauthorized field mutation;
- exact preview/commit parity;
- complete rollback recovery;
- invariant preservation under malformed, irrelevant, stale, or contradictory evidence;
- zero real service calls and external side effects; and
- no dependence on learned confidence for commit authority.

Track B may proceed independently of Track A because it can use the already supported controlled interface.
It must not use provisional concepts from Track C.

## Track C: shadow-only definition-conditioned ontology acquisition

### Question

Given a frozen typed ontology, definitions, examples, counterexamples, and interventions, can the system
retain and distinguish candidate extensions without granting them authority?

The target representation must factor two separate axes:

1. **Expressibility relative to the frozen DSL**
   - alias of an existing concept;
   - composition of existing concepts; or
   - not expressible in the bounded current DSL and therefore requiring a provisional primitive.
2. **Evidence status**
   - sufficient;
   - ambiguous or underspecified; or
   - contradictory.

"New primitive" means only not expressible inside the frozen bounded language. Examples cannot prove
absolute novelty, and multiple observationally equivalent schemas must remain in a version space or
posterior until a distinguishing intervention exists.

### Required architecture

```text
frozen ontology + definition + examples/counterexamples
    -> deterministic parser and ontology retrieval controls
    -> bounded exact schema enumeration
    -> optional LLM candidate set
    -> type, arity, reference, circularity, and contradiction checks
    -> exact comparison on held-out examples and interventions
    -> posterior/version space over candidate schemas
    -> sandbox namespace only
```

Deterministic checks establish well-formedness and consistency with the frozen evidence; they do not by
themselves establish semantic truth. Candidate minimality, duplicate detection, held-out execution, and
intervention discrimination are required.

### Essential controls and metrics

Controls:

- deterministic definition parser;
- retrieval over the existing ontology;
- bounded exact composition enumeration;
- direct LLM top-1;
- LLM candidate set;
- LLM candidates plus exact validation;
- oracle candidate set; and
- oracle definition.

Metrics:

- target-schema candidate recall;
- exact type and arity;
- semantic execution equivalence;
- alias/composition/provisional-primitive discrimination;
- false primitive creation;
- contradiction and insufficiency detection;
- held-out and intervention accuracy;
- entity-renaming and paraphrase robustness;
- candidate-set size and calibration;
- inference and interaction cost; and
- zero permanent registration and zero execution.

Because independent human contributors are unavailable, project-authored or model-generated definitions may
support development only. Fresh confirmation requires independently sourced definitions with automatic
ground truth or genuinely independent contributors. No synthetic record may be represented as human-authored.

## Integration sequence

The tracks integrate only in this order:

1. Track A establishes bounded external-language behavior or closes with an explicit safe fallback.
2. Track B establishes reversible fixed-ontology state control in a simulator.
3. Track C establishes high candidate recall and sufficiently low false primitive creation in shadow mode.
4. A new Bayesian study may choose questions, examples, or interventions to distinguish remaining ontology
   candidates while charging interaction costs.
5. Only a separately protected pass may allow provisional concepts to affect reversible simulated state.
6. Permanent ontology registration or real execution remains outside the current program and requires an
   independent approval authority.

1. Freeze a small typed DSL and exact bounded composition language.

5. Only if those gates pass, preregister one local model as a candidate-set proposer on a prospectively defined
   residual. Its output cannot register a primitive.
6. Use the resulting fixed, trusted ontology—not provisional concepts—in Track B's reversible sandbox decision
   study with ask, inspect, preview, commit, verification, and rollback costs.

post-hoc prompt, model, reasoning, parser, threshold, confidence, or gate changes on V164.
